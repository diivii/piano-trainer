# Piano Trainer: notes for Claude

Personal piano practice web app. Reads a digital piano (Kawai CN201) over Web MIDI,
shows MusicXML sheet music (OpenSheetMusicDisplay) and follows along as you play.
Main target is an **iPad in the "MIDIWeb Browser" app** (Safari has no Web MIDI;
switched from the old "Web MIDI Browser" on 2026-10-20 because MIDIWeb reopens the
last page, so a Shortcuts home-screen icon can open the app directly);
desktop Chrome/Edge is used for development.

Live: https://diivii.github.io/piano-trainer/

`README.md` has the feature list, the file-by-file layout and how deploying works.
Keep it up to date when features or files change. This file covers how to work on
the project and where it stands.

## How to work here

- Plain HTML/CSS/JS ES modules, no build step, no npm, no framework. Only dependency
  is the bundled `vendor/opensheetmusicdisplay.min.js`.
- Run locally: `python tools/serve.py` (or `start-server.cmd`), then http://localhost:8000.
  `.claude/launch.json` has a preview config for it.
- No automated tests. Check changes in the browser using the built-in simulator
  (computer keyboard / mouse as piano) and the MIDI event log.
- **The UI is in German** (note names C, Cis, … B, H). New UI text must be German;
  code, comments and commit messages are English.
- `js/midi-input.js` is the only module that touches Web MIDI. Everything else gets
  normalized note events, so a native app later would only replace that file.
- Practice logic (`practice.js`, `tempo-practice.js`) has no display code; keep it that way.
- Profiles (Emil, Julia) are a fixed list in `storage.js`. Pieces are shared; every
  run has a `profile` field and settings are stored per profile. Anything new that
  counts as progress must be per profile too. Each profile has a color theme
  (`body[data-profile=…]` in `style.css`, overriding the color variables); use
  `var(--accent)` etc. for new UI instead of fixed colors. Exceptions on purpose:
  pressed keys stay blue and note feedback stays green/orange/red.
- Data lives in the browser's IndexedDB on the device (`storage.js`). Keep the backup
  format (`backup.js`) backwards compatible so old backups can still be restored.
- **Pushing to `main` publishes the live site** via GitHub Actions
  (`.github/workflows/pages.yml`). Only push when the user asks.
- Built-in samples are generated by `tools/make_samples.py`; edit that script and
  re-run it rather than editing `samples/*.musicxml` by hand. Only public-domain
  music (the site is public): no Joe Hisaishi, film or pop songs. The user can
  import such pieces themselves; they stay private on the device.

## Current status (2026-10-20)

All built on 2026-10-19:

- Done: library with per-piece stats, sheet music import (`.musicxml`/`.xml`/`.mxl`),
  wait mode, tempo mode with metronome and timing judgement, colored notes, hands
  separately, bar loops, key hints, run history, backup/restore, focus mode / note zoom,
  17 built-in sample pieces (children's songs, Christmas, folk, classical), German UI, "Anhören" (playback via MIDI out or Web Audio),
  versioned loading so the iPad always gets the latest deploy.
- Done: MIDI on the iPad works in the Web MIDI Browser (confirmed 2026-10-20). It
  needed workarounds for that app's Web MIDI polyfill in `midi-input.js`: old-style
  iterators, continuous device polling, ignoring the add-on's callback errors.
  Keep them when changing MIDI code.
- MIDIWeb Browser lists outputs "Netzwerk Session 1", "CN201 MIDI Bluetooth",
  "MIDIWeb Out"; `pianoOutput()` skips the virtual ones (playback first went to the
  network session). The player also sends notes when due, without `send()`
  timestamps. Playback on the real piano not yet confirmed. The connection
  dialog's "Technische Details" shows the output port and send count/errors.
- Keep-awake: Screen Wake Lock while a piece is open; unconfirmed in MIDIWeb.
- Done (2026-10-20): profiles for Emil 🦖 (green theme) and Julia 🦄 (purple theme)
  with a switch button in the header (locked while a piece is open). The DB upgrade to version 2 dropped all
  runs recorded before profiles existed (agreed with the user); runs in old
  version 1 backups are skipped on restore, their pieces still come back.
- Done (2026-10-20): levels. Points per run are stored on the run (`points`), the
  level is computed from the profile's total (`levels.js`). Level-up shows on the
  results card with a jingle (`Player.playJingle`, piano or device like "Anhören").
  Looping runs ended by leaving the piece also earn points; a level-up there
  shows the level dialog (`#level-dialog`). A level-up always offers
  "Sicherung speichern" (iOS only saves files from a tap, so no silent autosave).
  `recordRun` must read `pieceRecord`/`piece` before its first `await`: leaving
  the piece clears them while it still runs (this once lost all looped runs).
- Done (2026-10-20): difficulty sections in the library. Pieces store `difficulty`
  ('easy' | 'medium' | 'hard'), estimated by `difficulty.js` in the background
  (hidden ScoreView) for any piece without one; `difficultyManual: true` when set
  by tapping the card's label. The samples come out 6 easy / 8 medium / 3 hard
  (Für Elise, Bach Präludium, Bergkönig).
- Done (2026-10-20): stars per piece (`levels.js` `stars()`), left-hand hints in
  orange (`keyboard-view.js` `setExpected(notes, left)`).
- Decided against for now: offline mode (service workers probably unavailable in
  MIDIWeb Browser's WKWebView).
- Done (2026-10-20): settings dialog (⚙ in the library) with "Fortschritt
  zurücksetzen" for the active profile (`storage.deleteRuns`). Deliberately hard
  to reach: collapsed section plus two taps. Put other rarely used options there.
- No known TODOs in the code.
